# ADR-0013：源站响应缓存

- 状态：Accepted
- 日期：2026-09-24
- 决策者：LYY
- 关联文档：`docs/evaluation.md`, `docs/adr/0009-evaluation-scale-and-task-metric-separation.md`, `docs/adr/0012-semantic-relevance-filtering.md`

## 背景

接入真实检索流程后，做了一次 B3 与 A6 的小规模对比。结果不可用：

| 指标 | A6（无语义过滤） | B3（有语义过滤） |
|---|---:|---:|
| 存储论文 | 14 | 10 |
| 保留论文 | 14 | 7 |
| claims | 7 | 1 |

**两次运行检索到的论文数量不同（14 对 10）。** 两个系统各自向源站发起请求，而 API
在两次请求之间返回了不同结果（限流、缓存、返回顺序都会影响）。

这意味着 claims 从 7 降到 1 无法归因于语义过滤——B3 本身检索到的输入就更少。
**消融实验要求两个臂看到完全相同的输入**，当前实现做不到。

同一问题还影响正式评测的规模：核心配置为 8 个（含 A6 后为 9 个），30 题各跑 3 次，
同一问题的多个配置会重复发起相同的源站请求，既有配额压力，也放大了运行间不一致。

此前已把限流治理到阈值以下，但限流解决的是"请求被拒"，不解决"同样的问题两次得到不同答案"。

## 决策

引入源站 HTTP 响应缓存，作为可复现评测的基础设施。

### 1. 位置与粒度

在 HTTP 层实现，作用于所有源站客户端，不逐个适配器改造。

缓存键：`method + URL（含查询参数）`。不含认证头——API key 影响配额，不改变内容。
不需要额外的规范化层，因为各客户端已经生成稳定的查询 URL。

### 2. 存储

内容寻址文件系统，路径 `data/cache/http/<sha256>.json`，与项目"本地优先 + 不可变文件"
的既有原则一致，且**不触碰数据库 schema**。

每个缓存条目保存：响应体（或 base64 编码的二进制）、状态码、内容类型、抓取时间、请求 URL。

### 3. 只缓存成功响应

仅缓存 2xx。失败（限流、超时、5xx）不写入缓存，以便重试仍有意义。

### 4. 命中与未命中必须可见

缓存会改变系统行为，因此不能静默。每次运行在 `search_sources` 步骤的输出中记录：

```json
{"cache_hits": 12, "cache_misses": 3}
```

该字段进入 `plan_step.output_json`，无需 schema 变更。评测报告必须包含它，
否则无法判断某次运行是冷缓存还是热缓存。

### 5. 有效期

- 交互使用：默认 TTL 7 天，过期条目视为未命中并重新抓取。
- **评测使用：TTL 关闭，缓存目录冻结。** 评测期间同一键必须始终返回同一字节。

### 6. 消融实验的输入一致性

这是本 ADR 的核心目的。消融流程改为：

```text
预热：对每个（问题 × 允许源）发起一次请求，填满缓存
  → 冻结该缓存目录
  → 各配置运行，全部读同一份缓存
  → 报告中记录缓存目录的哈希
```

任何在冻结缓存中缺失的请求记为未命中并如实上报；不得在正式对比期间回源，
否则两个臂的输入又会分叉。

### 7. 不与"缓存作为消融条件"混淆

缓存是实验控制手段，不是被测系统的一部分。**不新增消融条件。**

## 后果

正面：

- 消融的两个臂获得完全相同的输入，差异可归因于被测机制。
- 评测的源站请求量按配置数下降（同一问题多配置共享响应），缓解配额压力。
- 失败样本可重放：缓存目录哈希固定后，任何一次运行都可复算。
- 不触碰 schema，不引入向量库或外部服务。

负面：

- 缓存一旦损坏或过期，评测不可复现；因此评测必须冻结缓存并记录哈希。
- 缓存会掩盖源站行为的变化。正式评测期间源站内容变化本应视为干扰，
  冻结正是为了排除它，但论文中必须说明这一限制。
- `data/cache/` 会被 `.gitignore` 排除，缓存本身不进仓库；可复现性依赖记录哈希而非提交内容。
- 需要预热步骤，评测流程多一步。

## 备选方案

1. **不缓存，靠重复运行取平均**：不能消除输入差异，只是把方差平摊，拒绝。
2. **缓存写入 SQLite**：需要 schema 变更，且与不可变文件系统的既有选择冲突，拒绝。
3. **只缓存成功响应、失败也缓存**：缓存失败会让一次临时 429 固化为整个评测期间的
   永久失败，拒绝。
4. **在适配器层逐源实现**：五处重复逻辑，新增源站时容易遗漏，拒绝。

## 约束

- 缓存目录不得提交到 Git。
- 评测结果必须记录缓存目录哈希与命中/未命中计数。
- 冻结缓存后不得回源；缺失即未命中并如实上报。
- 缓存实现本身必须有单元测试，CI 不访问网络。
- 不得用缓存隐藏源站故障：未命中计数为 0 与非 0 的运行必须在报告中区分。

## 待决问题

1. **预热脚本的形态**：独立命令（如 `research-agent warm-cache`）还是评测命令的一个阶段？
2. **TTL 默认值**：交互场景 7 天是否合适。
3. **缓存目录哈希的计算方式**：对全部条目内容取哈希，还是对排序后的键集合取哈希
   （后者更稳定但无法发现内容损坏）。
