# ADR-0016：用户前端采用独立 SPA，分两阶段交付

- 状态：Accepted
- 日期：2026-09-26
- 决策者：LYY
- 关联文档：`docs/architecture.md`, `docs/PRD.md`, `docs/roadmap.md`, `docs/adr/0011-portability-and-github-distribution.md`

## 背景

v1 范围要求“最小 Web UI：任务状态、来源列表、证据链可视化”（AGENTS.md §3，PRD FR-38），
当前只有 CLI，`src/research_agent/interfaces/` 为空包。项目后续还要面向普通用户：
用户应能在浏览器里提交研究问题、查看运行进度、浏览报告与证据链、导出结果，而不必使用命令行。

需要决定两件事：前端分几步交付，以及用什么技术栈。约束如下：

- 前端不得改变正式实验条件；2027-01-15 起功能和数据源冻结，2027-03-01 起核心代码冻结。
- 支持 Windows、Linux、macOS；配置路径相对项目根目录；密钥只在后端环境变量中。
- 证据链是主贡献：前端必须完整呈现 `Claim → Evidence Span → Paper → Source Record*`
  以及 full_text 的 `File → Document`，不得自行生成或改写证据。

## 决策

### 1. 分两阶段交付

| 阶段 | 内容 | 路线图 | 时间 |
|---|---|---|---|
| 第一版：证据链查看器 | 只读视图：Run 列表与状态、Plan 步骤进度、来源分布、候选论文、证据链 | `SC-04`，里程碑 M4 | 2026-12 至 2027-01-10 |
| 第二版：用户前端 | 在第一版上增加：提交研究问题、实时进度、报告浏览、导出下载、人工确认操作 | `FE-*`，里程碑 M8 | M7 之后 |

两版是**同一个前端工程**的连续迭代，不做一次性原型。第二版只新增 `web/` 内的代码
和本地 API 的任务类接口，不改变 Agent Core、证据链与评测逻辑；需要改动核心时另写 ADR。

### 2. 技术栈

- 前端：React + Vite + TypeScript，位于项目根目录 `web/`，独立构建。
- 后端：FastAPI 本地 HTTP API，位于 `src/research_agent/interfaces/`，复用现有 runtime 与 repository。
- 前端只通过 HTTP API 访问数据，不直接读取 SQLite 或文件系统。
- API 契约在实现前写入文档（第一版开始前完成，路线图 `FE-01`），字段使用 `snake_case`，
  与数据模型术语一致。

### 3. 安全与本地优先

- API 默认只监听 `127.0.0.1`，v1 单用户、不做登录；CORS 只允许本地前端来源。
- 模型与源站密钥只存在于后端进程环境变量，前端和构建产物中不得出现。
- 删除原始文献、公开发送等需要人工确认的操作（`docs/PRD.md` §7）在前端只能发起“待确认”请求，
  确认逻辑由后端 Policy 执行并写审计日志。

### 4. 工程与可移植性

- Node.js 版本固定并写入 `web/` 的版本声明文件；依赖锁定文件提交到 Git，`node_modules/` 与构建产物不提交。
- 前端的检查（类型检查、lint、单元测试、构建）加入本地检查脚本与 CI。
- 安装 Node.js 属于新增全局依赖，修改 CI 也在开发红线之内（AGENTS.md §7），两者都在实施前获得确认（路线图 §5 D7、D8）。
- 没有 Node.js 的环境仍可完整使用 CLI；Python 包不依赖前端构建产物。

## 后果

正面：

- 交互能力足以支撑“提交问题、看进度、浏览证据链”的完整用户流程。
- 前后端通过 API 解耦，前端迭代不影响核心代码冻结与实验条件。
- 第一版与第二版复用同一工程，避免重写。

负面：

- 引入第二套工具链（Node.js），CI 时间和维护成本上升。
- 需要先设计并维护本地 API 契约。
- 三平台构建都要验证，Windows 路径与换行问题需要额外注意。

## 备选方案

1. FastAPI + 模板 + HTMX（纯 Python）：工具链最简单，但复杂交互（证据链图、实时进度）实现成本高；用户选择 SPA。
2. 最小 Web UI 与用户前端分别实现：拒绝，会产生一次性代码。
3. 把用户前端并入 M4 在 2027-01-15 前完成：拒绝，挤占正式实验前的修复与评测时间。
