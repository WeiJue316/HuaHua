# ADR-0006：评测驱动开发与消融实验

- 状态：Accepted
- 日期：2026-09-23
- 决策者：LYY
- 关联文档：`docs/evaluation.md`, `docs/roadmap.md`

## 背景

毕业设计项目容易只做出可演示系统，却缺少可复现实验。若等到实现完成后再设计评测，通常会出现：

- 指标与系统输出不匹配。
- baseline 不公平。
- 消融无法实施。
- 论文数字和代码版本不一致。
- 时间不足导致实验仓促。

## 决策

从设计阶段就采用评测驱动开发：

- 使用 LitSearch、AutoResearchBench 和自建 CS/AI 问题集。
- 定义 B0–B3 baseline。
- 定义 A1–A5 消融，其中 A1–A4 必须完成。
- 正式集规模、运行次数和任务指标拆分由 ADR-0009 进一步约束。
- 指标覆盖检索、证据、任务、延迟和成本，并区分 baseline-neutral 的任务完成率与证据合规率。
- 正式问题集冻结后不得根据结果反复修改。
- 每个 Run 保存配置、模型版本、prompt 版本、源站版本和原始结果。
- 从 2026-12 起每周写论文正文和实验记录。

## 后果

正面：

- 系统实现围绕可测指标展开，减少无效功能。
- 论文图表和结果可追溯到运行记录。
- 能清楚证明证据链和联邦路由的贡献。
- 中期后可以集中做实验而不是重新设计。

负面：

- 早期需要投入数据标注和评测脚本。
- 严格记录会增加少量开发开销。
- 自建问题集可能存在偏差，需要公开限制。

## 备选方案

1. 实现完成后再设计评测：时间风险高，拒绝。
2. 只做案例展示：不能支持论文结论，拒绝。
3. 只使用公开 benchmark：无法覆盖证据链，拒绝单独使用。

## 约束

- 未定义指标的复杂功能不得进入 P0。
- 新增 baseline 或指标必须更新 `docs/evaluation.md`。
- 实验结果不得手工删除失败样本。
- 论文中的每个数字必须关联配置文件、结果文件和运行记录。
