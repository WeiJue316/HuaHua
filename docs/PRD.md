# 面向计算机/AI 文献调研的可追溯科研 Agent 框架——产品需求文档

| 字段 | 内容 |
|---|---|
| 文档版本 | v0.1 |
| 状态 | 设计基线 |
| 日期 | 2026-09-23 |
| 项目性质 | 本科毕业设计 + 可运行独立 Agent 系统 |
| 实验范围 | 计算机/AI 文献调研 |
| 目标用户 | 单用户、单项目、单机环境下的科研人员或学生 |

## 1. 结论摘要

本项目要实现一个独立的科研助理 Agent，围绕“调研、查询、下载、归档、汇报”形成可运行闭环。系统以证据链为核心贡献，以多源 MCP 联邦与路由为支撑贡献，以状态机 + Plan-and-Execute 作为运行时骨架。

Pi 仅作为设计参考，不进入运行时依赖。项目不会通过 fork Pi 后改名来制造自研外观，而是独立实现 Agent Runtime、规划、执行、记忆、路由、策略、评测和证据链模块。

## 2. 问题定义

现有科研工具通常存在以下断层：

1. 搜索工具只返回论文列表，不能保证后续结论与原文位置绑定。
2. LLM 总结工具容易生成无法验证的陈述，引用与结论之间缺少可审计关系。
3. 多源检索需要人工重复查询、去重、比较版本和整理元数据。
4. PDF 下载、文件归档、笔记和报告彼此割裂，难以复现一次调研过程。
5. 单一 ReAct 或纯 LLM 流程在检索、限流、重试、状态恢复方面不稳定。

本项目要解决的核心问题不是“让 LLM 会搜索”，而是：

> 如何让科研 Agent 的每一次检索、筛选、下载、抽取和综合都可追踪、可复现、可评测？

## 3. 目标与非目标

### 3.1 产品目标

- 用户给出一个计算机/AI 研究问题后，系统能自动生成调研计划并调用多个学术数据源。
- 系统能合并跨源结果、识别重复论文、保留来源 provenance，并形成候选集。
- 系统能下载开放获取全文，归档不可变 PDF，并建立文件与论文的关联。
- 系统能从全文或摘要中抽取证据片段，生成带 locator 的证据表。
- 系统生成 Markdown 证据报告，确保每条关键结论绑定 Paper + Evidence Span。
- 系统记录完整运行轨迹，支持失败恢复、审计和实验复现。
- 系统提供至少一个最小 Web UI，用于查看任务状态、来源和证据链。

### 3.2 研究目标（由评测验证）

- 验证证据链机制能否降低无支撑结论率、提高引用准确率。
- 验证多源 MCP 联邦与路由能否提高检索覆盖率和结果鲁棒性。
- 验证 Plan-and-Execute 运行时能否在任务成功率和成本之间取得更优平衡。

### 3.3 非目标

- 不做通用个人助理，不处理非科研任务。
- 不做多 Agent 自治社会，不实现开放式自我反思循环。
- 不训练基础模型，不进行模型微调。
- 不在 v1 引入向量数据库。
- 不破解付费墙、验证码、DRM 或机构访问控制。
- 不承诺覆盖全部理工科；第一版只做计算机/AI。
- 不把 Zotero 或 BibTeX 作为主存储。
- 不把 Word、PDF、PPT 汇报作为第一优先级。

## 4. 用户与典型场景

### 4.1 用户画像

- 用户：需要完成文献调研、开题、论文写作的计算机/AI 学生。
- 环境：单机、本地优先、单项目工作区。
- 输入：自然语言研究问题、关键词、限定条件或已有论文列表。
- 输出：候选论文、下载文件、证据表、调研报告和导出结果。

### 4.2 典型场景

**场景 A：快速调研**

用户输入“近三年多模态 RAG 的评测方法有哪些？”。系统规划查询词，调用多个源站，合并结果，筛选 10–20 篇论文，生成证据报告。

**场景 B：定向下载与归档**

用户提供 DOI 或 arXiv ID。系统查询元数据，定位开放获取 PDF，下载并计算哈希，归档到项目目录，生成 BibTeX。

**场景 C：证据核验**

用户查看报告中的某条结论，点击引用后能看到对应论文、原文片段、页码或段落定位、抽取方法和来源链接。

**场景 D：实验复现**

研究者运行同一问题集，系统保存每次 Run 的配置、源站调用、去重结果、模型版本、成本和输出，用于比较 baseline 与完整系统。

## 5. 功能需求

### 5.1 项目与研究问题

- **FR-01**：系统必须支持创建、打开、归档一个本地研究项目。
- **FR-02**：项目必须包含研究问题、范围、时间范围、语言、目标数量和数据源白名单。
- **FR-03**：研究问题和每次修改必须记录版本、时间和关联 Run。

### 5.2 规划与执行

- **FR-04**：系统必须将研究问题分解为可执行步骤，形成带依赖关系的 Plan。
- **FR-05**：Plan 至少包含查询构造、源站路由、结果合并、候选筛选、获取全文、证据抽取和报告生成。
- **FR-06**：Executor 必须按状态机推进步骤，支持暂停、恢复、失败重试和人工中止。
- **FR-07**：LLM 只负责需要语义判断的步骤；确定性步骤必须由代码完成。
- **FR-08**：系统必须保存 Plan、步骤状态、输入输出摘要、错误和耗时。

### 5.3 多源查询与路由

- **FR-09**：系统必须支持 arXiv、OpenAlex、Crossref、Semantic Scholar、DBLP 五个源站。
- **FR-10**：每个源站必须作为独立 MCP server 实现，拥有自己的认证、限流、字段映射和错误处理。
- **FR-11**：Router 必须根据研究问题、源站能力和策略选择源站，不得无条件调用所有源站。
- **FR-12**：Federation 必须并行调用选中源站，处理超时、重试、部分失败和限流。
- **FR-13**：系统必须保留源站原始记录和归一化记录之间的映射。
- **FR-14**：系统必须支持按 DOI、arXiv ID、标题和作者等键进行跨源去重与合并。
- **FR-15**：跨源合并不得丢失 provenance；冲突字段必须保留来源和置信信息。

### 5.4 候选筛选与获取

- **FR-16**：系统必须根据主题相关性、时效、引用、开放获取状态和来源可信度形成候选集。
- **FR-17**：候选筛选必须可解释，并记录每篇论文被保留或排除的理由。
- **FR-18**：系统必须优先获取开放获取 PDF；无法获取全文时必须标记原因。
- **FR-19**：系统必须支持下载任务的重试、限流和失败记录；仅当源站和下载协议支持时启用断点续传。
- **FR-20**：系统必须对下载文件计算 SHA-256，并记录 URL、时间、MIME type 和大小。
- **FR-21**：下载或移动原始文献前，必须遵守权限策略；删除原始文献必须人工确认。

### 5.5 归档与记忆

- **FR-22**：系统必须以 SQLite 保存元数据、实体关系、状态和 Run 记录。
- **FR-23**：系统必须以文件系统保存不可变 PDF、解析文本和 Markdown 笔记。
- **FR-24**：系统必须使用 SQLite FTS5 支持本地全文检索。
- **FR-25**：系统必须支持 BibTeX、JSON 和 CSV 导出；Zotero 作为外部导出视图。
- **FR-26**：系统必须支持按项目、主题、年份、作者、来源和状态查询本地归档。

### 5.6 证据链

- **FR-27**：系统必须建立 `Claim → Evidence Span → Paper → Source Record*` 关系；`full_text` 证据还必须关联 `File → Document`。
- **FR-28**：Evidence Span 必须包含原文片段、locator、抽取方法、置信度、来源版本和 `source_record_id`；metadata/abstract 证据必须关联 Source Record。
- **FR-29**：locator 至少支持页码、章节、段落和字符区间中的一种，并保留可复现信息。
- **FR-30**：报告中标记为支持或部分支持的关键结论，必须绑定至少一个 Evidence Span。
- **FR-31**：无法找到证据的结论必须标记为“未支持”或“待验证”，不得伪装为事实。
- **FR-32**：系统必须检测引用是否指向真实存在的 Paper；`full_text` 证据还必须指向存在的 File 和 Document。
- **FR-33**：系统必须能回答“这条结论来自哪篇论文、哪一段、通过什么方法抽取”。

### 5.7 报告与汇报

- **FR-34**：系统必须生成 Markdown 调研报告。
- **FR-35**：系统必须生成 JSON/CSV 证据表。
- **FR-36**：系统必须生成 BibTeX 引用文件。
- **FR-37**：报告必须包含检索范围、源站、筛选标准、限制和未解决问题。
- **FR-38**：系统必须提供最小 Web UI，展示任务状态、候选论文、来源分布和证据链。按 ADR-0016 作为用户前端的第一版实现。
- **FR-39**：Word、PDF、PPT 汇报列为后续扩展，不阻塞 v1 验收。

### 5.8 策略、安全与审计

- **FR-40**：Policy 模块必须区分自动操作和需要人工确认的操作。
- **FR-41**：密钥必须来自环境变量或系统凭据管理器，不写入数据库、日志和代码。
- **FR-42**：系统必须记录源站调用、模型调用、下载行为、文件哈希和用户确认。
- **FR-43**：日志必须脱敏，并支持按 Run 查询。
- **FR-44**：系统不得绕过付费墙、验证码或访问控制。v1 不实现自动机构登录；如使用机构订阅内容，只复用用户已授权的本地会话或由用户手动导入的文件，并逐次确认。

### 5.9 评测

- **FR-45**：Evaluator 必须支持按问题集批量运行系统。
- **FR-46**：Evaluator 必须记录 Recall@K、Precision@K、Task Completion Rate、Evidence Coverage、Evidence Compliance Rate、Citation Accuracy、Unsupported Claim Rate、Task Success Rate、延迟和 token 成本。
- **FR-47**：Evaluator 必须支持 baseline 与完整系统的对比，以及至少四组消融实验。
- **FR-48**：所有评测运行必须保存可复现配置和原始结果。

### 5.10 用户前端（v1 之后，ADR-0016）

以下需求不阻塞 v1 验收，对应路线图 Phase 6 与里程碑 M8。

- **FR-49**：用户必须能在浏览器中提交研究问题，并设置源站、结果数量和是否启用相关性过滤与综合。
- **FR-50**：前端必须实时展示 Run 与各步骤的状态，并用用户能理解的语言说明失败原因。
- **FR-51**：用户必须能在前端浏览报告，并从任一 Claim 逐级追溯到 Evidence Span、Paper、Source Record；full_text 证据还能追溯到 File 与 Document。
- **FR-52**：用户必须能在前端下载 Markdown 报告、JSON/CSV 证据表和 BibTeX。
- **FR-53**：需要人工确认的操作在前端只能发起待确认请求，由后端 Policy 执行并记录审计。
- **FR-54**：前端只通过本地 HTTP API 访问数据，不直接读取数据库或文件系统；前端和构建产物中不得出现密钥。

## 6. 非功能需求

- **NFR-01 可复现性**：同一配置、同一数据源快照下，应能复现相同实体关系和报告结构。
- **NFR-02 可追溯性**：任意支持性 Claim 必须能追溯到 Evidence Span、Paper 和 Source Record；`full_text` 证据还必须能追溯到 File 和 Document。
- **NFR-03 可恢复性**：单步失败不得导致整个 Run 丢失；支持从中断状态继续。
- **NFR-04 性能**：单次五源检索在正常路径（无重试）目标 P95 小于 30 秒；降级路径（含有限重试）目标 P95 小于 90 秒；超时和限流必须可观测。
- **NFR-05 成本**：默认使用本地确定性流程；LLM 调用需记录 token 和费用，并支持预算上限。
- **NFR-06 可维护性**：MCP server、存储、模型和 UI 通过接口解耦，便于替换。
- **NFR-07 安全性**：不记录密钥和 Cookie；外部请求遵守源站条款和限流。
- **NFR-08 可用性**：CLI 是 v1 第一入口；v1 的 Web UI 只承担可视化和人工确认。v1 之后的用户前端（ADR-0016）成为普通用户的主要入口，CLI 保持完整可用。
- **NFR-09 可测试性**：核心模块必须有单元测试；关键流程必须有集成测试和端到端测试。

## 7. 自主性边界

| 操作 | 默认行为 | 是否需要确认 |
|---|---|---|
| 查询公开元数据 | 自动执行 | 否 |
| 读取公开摘要 | 自动执行 | 否 |
| 下载开放获取 PDF | 自动执行，记录来源 | 否 |
| 使用已授权机构会话下载 | 逐次记录并受策略限制 | 首次或高风险时确认 |
| 移动或重命名原始文献 | 生成操作建议 | 是 |
| 删除原始文献或项目数据 | 禁止自动执行 | 是，必须明确确认 |
| 本地生成报告 | 自动执行 | 否 |
| 公开发送报告或上传第三方 | 生成待发送内容 | 是 |
| 修改数据库 schema | 生成迁移方案 | 是 |
| 修改密钥、CI/CD 或系统配置 | 不自动执行 | 是 |

## 8. 用户主流程

```text
创建项目
  → 输入研究问题与范围
  → 生成 Plan
  → Router 选择源站
  → 并行查询 Router 选中的 MCP server（完整版最多五源）
  → 归一化、去重、合并 provenance
  → 筛选候选论文
  → 获取开放获取 PDF
  → 解析并归档
  → 抽取 Evidence Span
  → 生成 Claim 与引用关系
  → 校验引用完整性
  → 输出 Markdown / JSON / CSV / BibTeX
  → Web UI 查看证据链
```

## 9. 研究问题

- **RQ1（主）**：证据链机制是否能降低无支撑结论率并提高引用准确率？
- **RQ2（次）**：多源 MCP 联邦与路由是否能在源站异构和部分失败条件下提高检索覆盖率与鲁棒性？
- **RQ3（支撑）**：状态机 + Plan-and-Execute 运行时是否比单次 LLM 流程或纯 ReAct 提高任务成功率并控制成本？

## 10. 验收标准

### 10.1 功能验收

- 能用 CLI 创建项目并输入一个研究问题。
- 能至少调用两个源站完成一次真实查询，五源全部可用是完整版目标。
- 能识别同一论文的 DOI 或 arXiv ID 重复记录，并合并 provenance。
- 能下载至少一篇 arXiv 开放获取 PDF，记录 SHA-256 并归档。
- M2 原型至少生成 5 条可定位 Evidence Span；最终验收至少生成 10 条。
- 能生成至少一份包含 5 条关键结论的 Markdown 报告，每条支持性结论可追溯到证据，未支持结论显式标记。
- 能在 Web UI 中查看一条完整证据链。

### 10.2 实验验收

- 完成完整系统与至少三个 baseline 的对比。
- 完成至少四组消融实验：去证据链、去规划器、去路由器、无引用约束。
- 报告包含数据集、指标定义、统计结果、错误分析和限制。
- 所有实验能通过保存的配置和脚本复现。

## 11. 风险与约束

- **时间风险**：正式实验需在 2027-02-28 前完成（`docs/roadmap.md` M5）；论文写作排期见 `docs/thesis-plan.md`，不在本文件约束。
- **数据源风险**：DBLP 缺少摘要和全文；OpenAlex、Crossref 主要提供元数据；只有 arXiv 在 v1 中提供稳定 PDF 下载。
- **PDF 解析风险**：不同出版社 PDF 的版式和文本层质量差异大，需要可降级的 locator 策略。
- **LLM 风险**：模型可能生成无支撑陈述，因此引用约束和自动校验必须是系统级机制。
- **法律与合规风险**：不抓取付费墙内容，不绕过访问控制；机构订阅场景只复用用户授权。
- **范围风险**：多 Agent、向量数据库、全套 Office 导出都会稀释主贡献，v1 不纳入。
